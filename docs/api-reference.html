Магазин цифровых товаров

Ядро магазина: заказы по SKU, вебхук оплаты, автоматическая выдача ключей через двух поставщиков-заглушек, восстановление после сбоев и сверка денег. Все примеры ниже сняты с работающего API, а не составлены вручную.

Что гарантирует API

Вебхук идемпотентен

Повтор с тем же event_id возвращает duplicate: true и не меняет ничего. Доставка at-least-once — это норма, а не ошибка.

Порядок не важен

Событие по ещё не созданному заказу сохраняется и применяется при его создании. Ни потери, ни дубля.

Таймаут ≠ отказ

Повтор идёт с тем же request_id, поставщик обязан вернуть тот же код. Второй ключ не выпускается.

Скидку считает сервер

Сумма и промокод от клиента не принимаются на веру: лимит списывается атомарно, цена пересчитывается на сервере.

Жизненный цикл заказа

Поле status в ответах /orders принимает одно из семи значений. Пунктиром обведены восстановимые состояния — заказ в них не падает и доводится до выдачи.

Оплата

Реального эквайринга нет. Оба маршрута ведут в один обработчик, поэтому кнопка «оплатить» из интерфейса даёт ровно те же гарантии, что и вебхук от платёжной системы.

POST/orders/{id}/payЭмуляция оплаты

Генерирует event_id и применяет вебхук по контракту. status — paid или failed; неуспех переводит заказ в финальный payment_failed без выдачи и без записи в журнал денег.

Запрос
{ "status": "paid" }
Ответ 200
{
  "accepted": true,
  "order_id": "ord_mth0l6683rhat0",
  "status": "paid",
  "duplicate": false,
  "applied": true
}
200400 invalid_pay_status404 order_not_found
POST/webhook/paymentВебхук платёжной системы

Отвечает быстро и всегда 200 для принятых событий — 5xx заставил бы платёжку повторять доставку. Пятьдесят параллельных событий по одному заказу дают ровно один факт выдачи и одну запись в журнале.

ПолеОписание
event_idобязательноУникален для события; повтор приходит с тем же значением.
order_idобязательноПубличный id. Заказа может ещё не существовать.
statusобязательноpaid или failed.
amount, currency, created_atопц.Сумма, валюта и бизнес-время события.
Первое событие
{
  "accepted": true,
  "duplicate": false,
  "applied": true
}
Повтор с тем же event_id
{
  "accepted": true,
  "duplicate": true,
  "applied": false
}
200400 invalid_webhook

Промокоды

Лимит соблюдается под параллельными запросами: код с max_uses: 3 под пятьюдесятью одновременными заказами применяется не более трёх раз.

POST/promo/validateПроверить без списания

Только предпросмотр скидки для интерфейса — использование списывается при создании заказа, а не здесь.

Запрос

Ответ 200

  "value": 10,
  "discount": 129,
  "final_amount": 1161,
  "used": 0,
  "max_uses": 100
}
Код не подошёл — статус несёт причину, тело её называет
{ "valid": false, "reason": "promocode_not_found" }

Админка

Без авторизации — по условию задания она не проверяется. Здесь живут сверка и ручное восстановление заказов, застрявших в восстановимых состояниях.

GET/admin/reconciliationСверка и баланс

Ищет расхождения в обе стороны: «оплачен, но не выдан» и «выдан, но не оплачен». balance.ok означает, что журнал денег сходится с суммой оплаченных заказов.

Ответ 200 — один заказ ждёт пополнения остатка
{
  "paid_not_delivered": [
    {
      "order_id": "ord_mth0l6683rhat0",
      "status": "out_of_stock",
      "amount": "1161",
      "currency": "RUB",
      "created_at": "2026-08-31T09:06:50.623Z",
      "updated_at": "2026-08-31T09:06:50.810Z"
    }
  ],
  "delivered_not_paid": [],
  "balance": {
    "ledger_total": 1161,
    "paid_orders_total": 1161,
    "ok": true
  }
}

Суммы в списках приходят строками — это BIGINT из Postgres, который драйвер не приводит к числу, чтобы не терять точность.

POST/admin/orders/{id}/redeliverПовторная выдача

Безопасна для out_of_stock и delivery_failed. Для уже выданного заказа возвращает changed: false и второго ключа не выпускает — повторный вызов ничего не ломает.

Поставлено в очередь
{
  "order_id": "ord_mth0l6683rhat0",
  "status": "out_of_stock",
  "changed": true
}
Уже выдан — ничего не делает
{
  "order_id": "ord_mth0l6683rhat0",
  "status": "delivered",
  "changed": false
}
200404 order_not_found409 cannot_redeliver_status_…
POST/admin/stock/{sku}/restockПополнить остаток

Добавляет коды обоим поставщикам — разными половинами, чтобы один код физически не мог оказаться в двух пулах, — и увеличивает зеркало остатков. count по умолчанию 1, максимум 1000.

Запрос
{ "count": 10 }
Ответ 200
{
  "sku": "KEY-CS2-PRIME",
  "added": 10,
  "suppliers": { "a": true, "b": true }
}

Коды ошибок

Все ошибки приходят одинаково: { "error": "…" }. Исключение — /promo/validate, который отдаёт { "valid": false, "reason": "…" }, потому что невалидный код для интерфейса не сбой, а обычный ответ.

СтатусКодКогда
400sku_requiredВ теле /orders нет строки sku.
400invalid_webhookНет event_id, order_id или status не paid/failed.
400invalid_pay_statusВ /pay передан статус, отличный от paid и failed.
400code_and_amount_requiredВ /promo/validate не хватает кода или суммы.
400invalid_amountСумма не число или отрицательная.
404order_not_foundЗаказа с таким order_id нет.
404sku_not_foundТовара с таким SKU нет в каталоге.
404promocode_not_foundПромокод не существует.
409idempotency_key_conflictКлюч идемпотентности уже занят другим заказом.
409promocode_limit_reachedЛимит использований промокода исчерпан.
409cannot_redeliver_status_…Заказ в статусе, из которого повторная выдача небезопасна.
500internal_errorНеобработанное исключение; попадает в структурированный лог со стеком.

Как поднять

cd backend && docker compose up -d --build
curl http://localhost:3000/health

Витрина поднимется на :8080, API — на :3000. Машиночитаемая спека лежит в репозитории: backend/openapi.yaml (OpenAPI 3.0.3, 11 операций). Проверки надёжности воспроизводятся командами npm test, npm run race-check и npm run supplier-failure-demo.
