Проект маркетплейс цифровых товаров для геймеров, ниша площадок пример GGSel
Спасибо за выполнение первого тестового задания!

О чем текущий этап
Первый этап показал базу витрину, оформление и выдачу. Второй проверяет более сложные и интересные ситуации, которые отделяют сильного разработчика витрина, которая живет в реальном времени, честная покупка последней единицы наперегонки и бронь с таймером. Все строится поверх уже готовой главной с каталогом
Стек
- Frontend HTML, CSS, JavaScript, тяжелые фреймворки не обязательны
- Backend Node.js или PHP или свой стек
- Оплата эмулируется заглушкой, как в первом этапе
Задачи
Задача 1. Живая витрина в реальном времени
Наличие и цены на складе меняются, и это должно сразу отражаться у всех, кто открыл сайт, без перезагрузки страницы. Когда товар заканчивается, он гаснет у всех одновременно
Что должно быть готово
1) Изменение цены или наличия сразу видно во всех открытых вкладках без перезагрузки
2) Когда остаток дошел до нуля, кнопка Купить становится недоступна у всех сразу
3) Если товар подорожал, пока лежал в корзине, новая цена видна до оплаты, а не после
4) Все это работает и после обновления страницы, и после обрыва связи
Задача 2. Покупка последней единицы наперегонки
Двое покупателей одновременно берут последний товар. Один должен его получить, второй понятный отказ, без зависаний и без списания у проигравшего
Что должно быть готово
1) Последнюю единицу получает только один покупатель
2) Второму сразу показывается понятное сообщение, что товар только что раскупили, с предложением другого продавца или возвратом к товару
3) Ни у кого не остается оплаченного заказа без товара из-за этой гонки
Задача 3. Бронь с таймером
При оформлении товар бронируется на несколько минут с обратным отсчетом на экране. Если оплата не пришла вовремя, бронь снимается и товар снова доступен всем
Что должно быть готово
1) На странице оформления идет видимый обратный отсчет брони
2) По истечении отсчета бронь снимается и товар возвращается в продажу для всех
3) Если оплатить успели, заказ уходит в выдачу и отсчет больше ни на что не влияет
4) Один и тот же товар не может быть забронирован под два заказа одновременно
Задача 4. Устойчивость покупки к любым действиям бонус
Покупку нельзя сломать двойным кликом, кнопкой Назад после оплаты, обновлением страницы или обрывом связи в момент оплаты
Что должно быть готово
1) Двойной клик, Назад, обновление и обрыв связи не создают второй заказ и не задваивают оплату
2) После любого из этих действий на экране виден верный статус заказа
3) Повторная оплата уже оплаченного заказа ничего не меняет
Задача 5. Мгновенный поиск по большому каталогу бонус
По каталогу в тысячи предложений поиск и фильтры выдают результат мгновенно, без задержек и морганий
Что должно быть готово
1) Результат обновляется по мере ввода, без задержек и мигания списка
2) Устаревшие ответы не перетирают более свежие
3) Выбранные фильтры сохраняются в адресе страницы и открываются по прямой ссылке
Что делать не нужно
- Реальная оплата не нужна, оплата эмулируется как в первом этапе
- Точность верстки пиксель в пиксель не требуется, достаточно близко к макету
- Мобильная и темная версии, отзывы и футер не нужны
- Заново переписывать первый этап не нужно, задачи строятся поверх него
Формат ответа
1) Ссылка на рабочую версию или инструкция запуска
2) Ссылка на репозиторий или архив
3) Как воспроизвести живое обновление витрины и покупку последней единицы наперегонки
4) Фактически затраченное время
5) Готовность на звонке внести небольшое изменение
Приложение
Макет, базовый каталог и контракты берутся из первого тестового, наполнение каталога и склад создаются самостоятельно

Бронь с таймером	нет понятия брони/дедлайна оплаты, нет авто-возврата товара
Устойчивость (двойной клик, Back, refresh, обрыв)	частично на бэке (идемпотентность), на клиенте не выстроен state machine покупки, нет авто-резюма
Поиск по тысячам без задержек и «морганий»	каталог из 12 позиций, клиентский фильтр, нет URL-состояния, нет борьбы со stale-ответами
«Предложение другого продавца»	в каталоге нет понятия продавца и группировки «тот же товар»
Важное ограничение: тесты 1-го этапа (в т.ч. stock.test.js) закрепляют семантику «заказ можно создать и оплатить даже при пустом остатке, а нехватка ключа обнаруживается при выдаче → восстановимый out_of_stock». Поэтому новую «предоплатную» семантику гонки/брони нельзя делать безусловным поведением POST /orders — иначе сломаем критерии этапа 1. Решение: аддитивное расширение (legacy-путь без параметра hold сохраняется байт-в-байт, новый маркетплейс-путь включается явно).

План реализации
Общая архитектура
Транспорт real-time — SSE (EventSource), не WebSocket.

Плюсы: ноль новых npm-зависимостей, встроенный авто-reconnect (закрывает «работает после обрыва связи»), идёт через обычный HTTP/nginx.
Новый эндпоинт GET /events: держит Set<Response>, шлёт heartbeat-комментарий каждые ~25 с (защита от прокси-таймаутов), при коннекте клиент дополнительно делает полный GET /products (снапшот-сверка после reconnect/refresh).
Публикация событий — после COMMIT транзакции (не внутри), источник истины — БД; in-process шина (EventEmitter). Для горизонтального масштаба апгрейд-путь — LISTEN/NOTIFY Postgres или Redis pub/sub (зафиксирую как note в README).
nginx: для location /events выключить буферизацию (proxy_buffering off;) и таймауты, если фронт будет проксировать SSE через nginx (сейчас фронт на nginx отдельно от API, так что достаточно настроек в app + CORS).
Новая учётная модель остатков (двухкомпонентная, остаётся в stock_mirror):

available — как сейчас: физический пул ключей (декремент при выдаче, инкремент при restock);
held (новое поле) — «коммитнутые, ещё не выданные» единицы: активные брони в виде заказов created+paid+delivering с холдом;
витринное число = available − held (сколько реально можно купить прямо сейчас). Оно же публикуется в SSE и именно оно «гаснет» при 0.
Инвариант «оплаченный заказ всегда получит товар»: количество выданных + held никогда не превышает пул ключей, т.к. холд снимает единицу с продажи до оплаты.
Бронь = заказ с холдом (рекомендуемый вариант). Альтернатива «отдельная сущность reservation» рассмотрена и отклонена: она дублирует жизненный цикл (бронь→заказ→оплата) и усложняет кейсы refresh/Назад. Выбранный вариант проще и ложится на существующие статусы/воркеры:

POST /orders { sku, hold: true, purchase_key, promocode? } → транзакция: SELECT stock_mirror FOR UPDATE → проверка available−held > 0 → вставка заказа со статусом created, hold_until = now()+TTL (по умолчанию 5 мин, env RESERVATION_TTL_MS), held+1. Ответ: заказ + hold_until + expires_in.
Если остатка нет → 409 { error: 'just_sold_out', alternatives: [...] } — мгновенный отказ «раскупили» с предложением другого продавца того же товара.
Идемпотентность: повторный POST /orders с тем же purchase_key возвращает тот же заказ 200 (двойной клик не создаёт второй заказ).
Оплата в срок: существующие /orders/:id/pay + /webhook/payment без изменений → created→paid → выдача. При финализации delivered: available−1, held−1 (тем же UPDATE).
Не успели оплатить: recovery-воркер раз в N секунд переводит created c истёкшим hold_until в новый статус expired, held−1, публикует SSE → товар снова в продаже у всех.
payment_failed на created → статус payment_failed, held−1 (бронь освобождена).
Повторная оплата уже оплаченного/выданного заказа — no-op (CAS уже есть; в ответ pay добавим текущий статус заказа).
Legacy POST /orders без hold — без изменений (этап 1 и его тесты целы).
Гонка «последней единицы» решается до оплаты атомарно строковым локом — ровно один победитель.
Живые цены: у позиции цена = products.price, меняется админкой (POST /admin/products/:sku/price) и/или автосимулятором. Заказ при создании фиксирует актуальную цену; клиент до оплаты показывает разницу «было → стало». Плюс «подтверждение оплаты» показывает финальную сумму с сервера — новая цена всегда видна до списания.

Каталог и продавцы: в products добавляются seller, product_group (для «того же товара у другого продавца»), существующие 12 SKU получают значения по умолчанию. Отдельный сид генерирует большой каталог (тысячи офферов: реалистичные названия × несколько продавцов с разными ценами/остатками) и пулы ключей у поставщиков A/B (скрипт по образцу seed-bench.js). Поиск — через расширение pg_trgm + GIN-индекс по name (подстроки на русском/латинице), сортировки и фильтры — по индексам.

Фронтенд-стратегия устойчивости покупки: единый client-state машины покупки на сессию в sessionStorage (purchaseKey генерируется один раз на попытку, orderId после создания). Обновление/Назад/обрыв → страница резюмируется по GET /orders/:id; обрыв при оплате → авто-опрос статуса и идемпотентный retry оплаты; повторный платёж уже оплаченного заказа ничего не меняет (сервер и клиент).

Фронтенд: файлы и поведение по задачам
Задача 1 (живая витрина) — новый frontend/live.js: класс LiveStore (EventSource на API+/events, авто-reconnect, на каждый open — refreshCatalog(), карта sku → {price, available, held}). События обновляют DOM карточек на лету (цена, бейдж «Осталось N», disabled у «Купить» при available≤0) и внутренний стор для ещё не отрендеренных карточек (пагинация). «Гаснет у всех» = событие о холде последней единицы мгновенно дизейблит кнопку во всех вкладках.
Задача 2 (последняя единица) — клик «Купить» → POST /orders {hold:true, purchase_key}; 201 → редирект на checkout.html?order=...; 409 just_sold_out → понятное сообщение «Только что раскупили» + кнопки-офферы других продавцов этого product_group и «Назад к товару» (кнопка к этому моменту уже погасла у всех). Проверка через тест и ручную демонстрацию в двух окнах.
Задача 3 (бронь с таймером) — новая страница frontend/checkout.html + checkout.js:
обратный отсчёт от серверного hold_until (а не локального — переживает refresh), авто-возврат на витрину с уведомлением при expired (событие SSE/опрос);
«Оплатить успех/неуспех» (эмуляция как в 1-м этапе), «Отменить бронь»;
живая цена (SSE) + «цена изменилась: X → Y, подтвердите оплату Y» перед платёжным шагом;
после оплаты — как раньше: выдача ключа, ссылка на order.html; таймер больше ни на что не влияет (paid/delivered не трогаются воркером).
Дубликат брони: один товар (одна единица) не может быть взят двумя заказами — гарантирует бэкенд-лок, на клиенте это видно как «раскупили».
Задача 4 (устойчивость) — state machine в checkout.js/app.js: purchaseKey в sessionStorage (переживает refresh), повторное открытие checkout по orderId из URL/sessionStorage резюмирует без нового заказа; двойной клик — disabled + идемпотентность; сетевой обрыв при pay — статус-опрос GET /orders/:id + кнопка «Проверить статус», повторный платёж безопасен (сервер вернёт фактический статус); «Назад после оплаты» — order.html показывает delivered с ключом (уже умеет, добавим статус expired).
Задача 5 (мгновенный поиск) — рефакторинг сетки товаров: frontend/catalog.js:
серверные запросы с debounce ~200 мс, AbortController (отмена устаревшего) + монотонный seq (ответ с меньшим seq отбрасывается — «устаревшие ответы не перетирают свежие»);

index.html — подключить live.js, catalog.js, новые атрибуты карточек (seller, остаток); order.html — статус expired; admin.html/.js — поле смены цены (+ список «зависших» броней по желанию).

Справедливая претензия — но давайте разделим «модно» и «правильно», потому что в этой задаче есть две принципиально разные категории проблем, и к ним применимы разные инструменты. Очередь не может решать то, что должно решаться синхронно и атомарно, а Redis не делает консистентной систему, источник правды в которой — Postgres. По пунктам.

Какие моменты здесь вообще решаются и чем
1. Гонка за последнюю единицу — это НЕ задача очереди
Решение «ты взял / ты не взял» обязано быть синхронным (клиент ждёт ответ до оплаты) и линеаризуемым на ресурсе (единица товара). Kafka/Celery/BullMQ тут принципиально не подходят: вынос решения в очередь означает, что пользователь не получает мгновенный ответ, а между «решили в очереди» и «оплатили» появляется окно, в котором можно создать тот самый «оплаченный заказ без товара».

Правильный прод-примитив — атомарный условный апдейт в хранилище, которое владеет инвариантом «не продать больше, чем есть»:


UPDATE stock_mirror
   SET held = held + 1
 WHERE sku = $1 AND available - held >= 1   -- ровно один выигрывает при остатке 1
RETURNING ...
Postgres сериализует конкурентов на блокировке строки: из двух одновременных запросов при available−held=1 пройдёт ровно один, второй перепроверит WHERE после освобождения лока и получит 0 строк. Никакой очереди, никакого «двухфазного» танца.

Можно ли вместо Postgres держать счётчик в Redis (Lua DECRBY с проверкой)? Да, это стандартный приём для горячих SKU на флеш-распродажах — но тогда Redis становится источником правды для остатка, и нужно дублировать изменения в Postgres с компенсациями. На нашем масштабе это добавляет риск рассинхрона, а не убирает. Вывод: гонку оставляем на атомарном апдейте Postgres — это и есть прод-паттерн, а не костыль.

2. Live-рассылка между репликами — вот где Redis реально нужен
SSE/EventSource решает транспорт до браузера (авто-reconnect — закрывает «после обрыва»). Но если API поднят в двух и более репликах (а это и есть «прод»), изменение на инстансе A должны увидеть клиенты, подключённые к инстансу B. Тут один из вариантов:

Redis pub/sub — стандартный фановый мост для realtime-шлюзов, дёшево и прозрачно;
PostgreSQL LISTEN/NOTIFY — не требует нового контейнера, но лимит payload и отсутствие персистентности; у нас всё равно есть полный снапшот GET /products при reconnect, так что это рабочий вариант, но Redis — чище и привычнее;
Kafka — для фанаута избыточен (нужен durable replay нескольким группам потребителей — см. п. 4).
Плюс важный прод-нюанс: при падении Redis/канала клиент не должен умирать — делаем graceful degradation: при потере SSE-соединения клиент откатывается на периодический поллинг изменённых офферов, а при open всегда сверяется полным снапшотом.

3. Таймеры брони — здесь осмысленны два слоя, а не один
Ленивое освобождение на read-пути: при любой попытке использовать/прочитать протухшую бронь — атомарно вернуть единицу и ответить «expired». Это краш-безопасно и не зависит от того, жив ли планировщик.
Периодический sweeper как backstop — ровно то, что уже делает recovery-воркер.
Если Redis уже введён ради п. 2, то заменить sweeper на BullMQ delayed jobs (Node-эквивалент Celery) имеет смысл: точный дедлайн на каждую бронь, ретраи, дэшборд, нет поллинга БД. Но это улучшение observability, а не корректности — корректность даёт ленивое освобождение + CAS. Отдельно: Celery в этом проекте не нужен в принципе — это Python-инструмент, а стек у нас Node; его роль играет BullMQ, и вводить Python в проект «ради прода» было бы расколом стека.

4. Очередь выдачи — в коде уже прод-паттерн, вопрос лишь в транспорте
Сейчас: transactional outbox (delivery_jobs создаётся в той же транзакции, что и created→paid) + воркеры с FOR UPDATE SKIP LOCKED. Это канонический паттерн (то же делает Stripe/Temporal-подобные системы), просто без внешнего брокера. Kafka имеет смысл здесь только в одной конфигурации: когда выдача — отдельный сервис/команда и нужен replay + несколько групп потребителей (доставка, аналитика, уведомления). Тогда правильный путь — не писать руками в Kafka из транзакции (это создаёт проблему dual-write), а CDC из outbox-таблицы (Debezium) → Kafka. Добавлять это сейчас ради тестового задания — архитектурный театр: инфраструктуры больше, а критерии приёмки (exactly-once) всё равно обеспечивают CAS и UNIQUE-констрейнты в Postgres, которые уже написаны и протестированы. Зафиксирую как документированный апгрейд-путь.

5. Идемпотентность и дедуп вебхуков
Уже решено правильно и без Redis: event_id UNIQUE, INSERT ... ON CONFLICT DO NOTHING, CAS-переходы статусов. Redis (SET NX + TTL) тут — только кэш-прослойка перед БД для разгрузки, не гарантия. Гарантия остаётся в констрейнтах.

6. Поиск на «тысячи»
Elasticsearch/Meilisearch/Redisearch имели бы смысл при сотнях тысяч+ SKU, фасетной фильтрации по десяткам атрибутов, typo-tolerance и ранжировании. На «тысячи предложений» (формулировка ТЗ) правильный инструмент — pg_trgm GIN-индекс + пагинация, и это доказывается EXPLAIN-тестом. Когда перерастём — переезд на Meilisearch/Typesense, индекс которого наполняется тем же событийным конвейером, что и доставка.

Что я меняю в плане после твоей претензии (убираю костыль)
Мой прежний вариант с флагом hold у POST /orders (две семантики на одном эндпоинте) — действительно компромисс ради совместимости с тестами этапа 1, и ты прав, что это некрасиво. Заменяю на полноценный first-class ресурс брони:

POST /reservations { sku, ttl? } → атомарный UPDATE stock_mirror ... WHERE available-held>=1 в транзакции, вставка reservations (id, sku, status active, expires_at) — гонка решается здесь и только здесь, ответ синхронный. Есть остаток → бронь + таймер; нет → 409 с альтернативными продавцами.
GET /reservations/:id → состояние брони + ленивое освобождение при истечении (read-path).
POST /reservations/:id/cancel → явная отмена, возврат единицы.
POST /orders { reservation_id, promocode? } → подтверждение: заказ создаётся по текущей цене (новая цена видна до оплаты), получает pay_until = expires_at брони, бронь переходит в confirmed. Повторный вызов с той же reservation_id идемпотентен (возвращает тот же заказ) — это и есть защита от refresh/Back/двойного клика на уровне API.
Оплата, выдача, out_of_stock/delivery_failed, повторные вебхуки — существующий конвейер этапа 1 без изменений (он и есть правильная реализация).
Expiry: sweeper (заказы created с истёкшим pay_until и брони active с истёкшим expires_at) + ленивое освобождение. Учёт единиц: held = активные брони + заказы created/paid/delivering; снимается при delivered, возвращается при expire/cancel/payment_failed.
Legacy прямой POST /orders по SKU остаётся как отдельный внутренний контракт (для совместимости с этапом 1 и его acceptance-критерием «пустой остаток у поставщика → восстановимый out_of_stock» — это другой слой отказа, он обязан остаться). Витрина 2-го этапа ходит только через reservation-флоу.
Это убирает «двуличие» эндпоинта: у нас два явных ресурса с явными жизненными циклами, как в проде (бронь — временное право, заказ — финансовый документ).

Финальный план реализации 2-го этапа
Ключевые архитектурные решения
Гонка и бронь — на Postgres, атомарно и синхронно (очередь здесь не участвует и не нужна): UPDATE stock_mirror SET held = held + 1 WHERE sku=$1 AND available - held >= 1 RETURNING ... Ровно один победитель при остатке 1; проигравший мгновенно получает 409 «только что раскупили» + альтернативных продавцов.
Бронь — first-class ресурс (reservations), заказ создаётся при подтверждении брони по текущей цене (новая цена всегда видна до оплаты). Никаких флагов-костылей у POST /orders: legacy-эндпоинт этапа 1 остаётся отдельным внутренним контрактом нетронутым.
Учёт остатков: available (физический пул ключей) − held (активные брони + заказы created/paid/delivering) = витринное «можно купить». Поддерживается транзакционно; гарантия «нет оплаченного заказа без товара» вытекает из инварианта выдано + held ≤ пул.
Real-time: GET /events (SSE, EventSource) + in-process шина (EventEmitter), публикация после COMMIT. Сердечные комментарии каждые ~25 c; клиент при каждом open/reconnect делает полный снапшот GET /products (переживает refresh и обрыв связи). Апгрейд-путь на multi-instance — LISTEN/NOTIFY (затем Redis pub/sub) — опишу в README/PLAN, реализовывать не буду.
Таймеры: ленивое освобождение на read-пути (любое чтение/подтверждение протухшей брони атомарно возвращает единицу) + sweeper в recovery-воркере как backstop. Expire/Cancel/payment_failed возвращают товар и публикуют SSE.
Устойчивость покупки: клиентский state machine (purchase_key в sessionStorage), идемпотентность на бэке (UNIQUE(purchase_key) у брони, reservation_id-ссылка у заказа, существующие CAS/event_id), авто-опрос статуса при обрыве.
Поиск по тысячам: серверный GET /products с параметрами + pg_trgm GIN-индекс; на клиенте debounce + AbortController + монотонный seq (старые ответы не перетирают новые) + список не очищается до прихода данных + состояние фильтров в URL. Elasticsearch/Meilisearch — только при сотнях тысяч+, это задокументирую как путь роста.

# Финальный план реализации 2-го этапа

## Ключевые архитектурные решения

1. **Гонка и бронь — на Postgres, атомарно и синхронно** (очередь здесь не участвует и не нужна):
   `UPDATE stock_mirror SET held = held + 1 WHERE sku=$1 AND available - held >= 1 RETURNING ...`
   Ровно один победитель при остатке 1; проигравший мгновенно получает `409` «только что раскупили» + альтернативных продавцов.
2. **Бронь — first-class ресурс** (`reservations`), заказ создаётся при подтверждении брони по **текущей** цене (новая цена всегда видна до оплаты). Никаких флагов-костылей у `POST /orders`: legacy-эндпоинт этапа 1 остаётся отдельным внутренним контрактом нетронутым.
3. **Учёт остатков**: `available` (физический пул ключей) − `held` (активные брони + заказы `created/paid/delivering`) = витринное «можно купить». Поддерживается транзакционно; гарантия «нет оплаченного заказа без товара» вытекает из инварианта `выдано + held ≤ пул`.
4. **Real-time**: `GET /events` (SSE, `EventSource`) + in-process шина (EventEmitter), публикация **после COMMIT**. Сердечные комментарии каждые ~25 c; клиент при каждом `open`/reconnect делает полный снапшот `GET /products` (переживает refresh и обрыв связи). Апгрейд-путь на multi-instance — `LISTEN/NOTIFY` (затем Redis pub/sub) — опишу в README/PLAN, реализовывать не буду.
5. **Таймеры**: ленивое освобождение на read-пути (любое чтение/подтверждение протухшей брони атомарно возвращает единицу) + sweeper в recovery-воркере как backstop. Expire/Cancel/`payment_failed` возвращают товар и публикуют SSE.
6. **Устойчивость покупки**: клиентский state machine (`purchase_key` в `sessionStorage`), идемпотентность на бэке (`UNIQUE(purchase_key)` у брони, `reservation_id`-ссылка у заказа, существующие CAS/event_id), авто-опрос статуса при обрыве.
7. **Поиск по тысячам**: серверный `GET /products` с параметрами + `pg_trgm` GIN-индекс; на клиенте debounce + `AbortController` + монотонный `seq` (старые ответы не перетирают новые) + список не очищается до прихода данных + состояние фильтров в URL. Elasticsearch/Meilisearch — только при сотнях тысяч+, это задокументирую как путь роста.

## Изменения схемы (`backend/schema.sql`, идемпотентные)

- `CREATE EXTENSION IF NOT EXISTS pg_trgm;`
- `products`: `+seller TEXT DEFAULT 'GameMarket'`, `+product_group TEXT`; индексы: GIN `(name gin_trgm_ops)`, `idx_products_group`.
- `stock_mirror`: `+held BIGINT NOT NULL DEFAULT 0`.
- `orders`: `+sku TEXT`, `+pay_until TIMESTAMPTZ` (только для заказов из брони); частичный индекс `idx_orders_pay_until ON orders(pay_until) WHERE status='created' AND pay_until IS NOT NULL`.
- Новая `reservations`: `id PK`, `sku`, `status ('active'|'confirmed'|'cancelled'|'expired')`, `purchase_key UNIQUE`, `expires_at`, `order_id`, таймстемпы; индекс `(status, expires_at)`.
- (Существующие таблицы этапа 1 не меняют семантику.)

## API

- `GET /products?q=&type=&seller=&sort=price_asc|price_desc|name&in_stock=1&limit=&offset=` → массив + `X-Total-Count`; `available` = `available−held`; добавлены `seller`, `product_group`.
- `POST /reservations { sku, purchase_key }` → атомарная бронь, `201 {id, expires_at, price, sku}`; повторный `purchase_key` → та же бронь (`200`); нет остатка → `409 {error:'just_sold_out', alternatives[]}`.
- `GET /reservations/:id` → состояние + ленивое освобождение при истечении.
- `POST /reservations/:id/cancel` → отмена, возврат единицы.
- `POST /orders { reservation_id, promocode? }` → подтверждение по текущей цене, `pay_until`; `409 reservation_expired` при просрочке; идемпотентен (повтор с той же `reservation_id` → тот же заказ `200`). Legacy `POST /orders { sku }` — без изменений.
- `POST /orders/:id/pay` — без изменений + в ответе фактический статус заказа (для resume после обрыва/Back).
- `POST /admin/products/:sku/price`, `POST /admin/stock/:sku/restock` (есть) — публикуют SSE.
- `GET /events` — SSE-поток.
