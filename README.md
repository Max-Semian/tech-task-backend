## Запуск одной командой

```bash
cd backend
docker compose up -d --build
```

| Сервис | Адрес | Что это |
|---|---|---|
| `frontend` | http://localhost:8080 | Витрина (nginx, статика из `frontend/`) |
| `app` | http://localhost:3000 | REST API + фоновые воркеры выдачи и recovery |
| `supplier-a` / `supplier-b` | внутри сети compose | Заглушки поставщиков (падают и «зависают») |
| `db` | :5432 | PostgreSQL 16 |

Проверка: `curl http://localhost:3000/health` → `{"ok":true}`, витрина — http://localhost:8080.
Каталог засеивается автоматически при старте на чистой БД.

> Витрина берёт адрес API из `window.API_BASE`, по умолчанию `http://localhost:3000`.
> Для запуска целиком локально менять ничего не нужно.

Локальный запуск без Docker для приложения, переменные окружения и полный список
эндпоинтов — в [backend/README.md](backend/README.md).

## Как воспроизвести проверки

Нужен только Postgres (`docker compose up -d db`). Оба скрипта самодостаточны: поднимают
одноразовую БД, свой экземпляр приложения и свои заглушки поставщиков, а после себя
убираются. Дев-база `shop` не затрагивается, запущенный `app` не мешает.

```bash
cd backend
npm test                        # 37 тестов: все критерии приёмки обоих ТЗ
npm run race-check              # 50 параллельных вебхуков -> ровно один факт выдачи
npm run supplier-failure-demo   # поставщик A всегда 5xx -> fallback на B, одна выдача
npm run reconcile               # сверка «оплачен, но не выдан» / «выдан, но не оплачен»
```

Ожидаемый результат: `37/37 pass`, два `✅ PASS`, в сверке `balance.ok: true`.

## Как обеспечена однократная выдача

Внешних брокеров нет — все гарантии держатся на Postgres:

1. **Идемпотентность вебхука.** `payment_events.event_id` — PRIMARY KEY. Повторная доставка
   того же события вставиться не может и не меняет ничего. Вебхук, пришедший раньше заказа,
   сохраняется с `order_fk = NULL` и применяется при создании заказа — без потери и без дубля.
2. **Один переход статуса.** Оплата переводит заказ CAS-апдейтом `UPDATE ... WHERE status='created'`.
   Из 50 параллельных вебхуков ровно один выигрывает и ставит задачу выдачи; остальные — no-op.
3. **Одна задача выдачи на заказ.** Частичный UNIQUE-индекс `uq_delivery_jobs_active` по
   `order_id WHERE status IN ('pending','processing')`. Воркеры забирают задачу через
   `FOR UPDATE SKIP LOCKED`, поэтому параллельные воркеры не берут одну и ту же.
4. **Ловушка таймаута.** `delivery_attempts.request_id` — PRIMARY KEY, а поставщик обязан на
   повтор с тем же `request_id` вернуть **тот же** код. Таймаут не считается отказом: повтор
   после него забирает уже выданный код, а не выпускает второй.
5. **Деньги сходятся.** `money_ledger` с `UNIQUE(order_id, entry_type)` — ровно один платёж
   на заказ, сумма журнала всегда равна сумме оплаченных заказов.

Восстановимые состояния `out_of_stock` и `delivery_failed` не роняют заказ: он остаётся
в очереди, доводится фоновым воркером после пополнения остатка либо вручную через
`POST /admin/orders/:id/redeliver` — повторно и безопасно, без задвоения.

### Витрина

Верхняя часть свёрстана по макету: шапка, баннер-карусель, ряд иконок сервисов, блок
пополнения, карточки товаров. Пять обязательных интерактивов на месте — карусель
(автопрокрутка, стрелки, точки), меню «Каталог» (открытие/закрытие по клику и вне меню),
переключатель валют, hover-выделение иконок и карточек. Покупка идёт с кнопки «Купить»:
создание заказа → оплата (кнопки «успех/неуспех» шлют вебхук по контракту) → автовыдача
ключа → страница статуса. Промокод применяется на сервере, клиентской сумме доверия нет.

Сверх ТЗ добавлены блок отзывов, футер и пересчёт валют — задание их не требовало.
