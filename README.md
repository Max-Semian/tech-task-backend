# Магазин цифровых товаров — тестовое задание (этапы 1 и 2)

Маркетплейс цифровых товаров для геймеров (ключи, пополнения, подписки, gift-карты) — ниша площадок типа GGSel.

- **Этап 1** (ядро): заказы, вебхук оплаты, exactly-once выдача под гонками, ловушка таймаута, восстановление, промокоды.
- **Этап 2** (маркетплейс): живая витрина (SSE), гонка за последнюю единицу, бронь с таймером, устойчивая покупка, мгновенный поиск по каталогу в тысячи офферов.

> Исходные ТЗ: [`docs/tz-backend.md`](docs/tz-backend.md), [`docs/tz-fullstack.md`](docs/tz-fullstack.md),
> [`docs/2-nd_part.md`](docs/2-nd_part.md). Чек-лист этапа 2 — [`docs/PLAN-stage2.md`](docs/PLAN-stage2.md).

## Быстрый старт (одна команда)

```bash
cd backend
docker compose up -d --build
```

| Сервис | Адрес | Что это |
|---|---|---|
| `frontend` | http://localhost:8080 | Витрина: nginx отдаёт статику и **проксирует API** (один-origin, `/api/*`) |
| `app` | http://localhost:3000 | REST API + воркеры выдачи/recovery + sweeper броней |
| `supplier-a` / `supplier-b` | внутри сети | Заглушки поставщиков (падают/«зависают», дедуп по `request_id`) |
| `db` | :5432 | PostgreSQL 16 |

При чистой БД автоматически засеивается базовый каталог (12 SKU) и **маркетплейс-каталог**
(`SEED_OFFERS`, по умолчанию 3000 офферов с продавцами). Остатки синхронизированы с пулами
ключей у поставщиков A/B (детерминированный генератор).

Проверка: витрина http://localhost:8080, `curl http://localhost:8080/api/health`.

Переменные для демо (переопределяются через env):

- `SEED_OFFERS` — размер маркетплейс-каталога (0 — только базовые 12);
- `LIVE_SIMULATE=1` — фоновый демо-процесс плавно меняет цены случайных офферов (видно в двух вкладках без действий);
- `RESERVATION_TTL_MS` — длительность брони (по умолчанию 5 минут; можно сократить для демо, минимум 20 с).

Локальный запуск без Docker, переменные окружения и полный список эндпоинтов — в [`backend/README.md`](backend/README.md).

## Как устроена витрина этапа 2

- **Живая витрина.** Браузер открывает `GET /api/events` (SSE). При изменении цены или остатка
  (бронь, выдача, отмена, restock, смена цены админом, симулятор) сервер после COMMIT публикует
  событие `{type:'offer', sku, price, available, held}` — карточки обновляются у всех без перезагрузки.
  EventSource сам переживает обрыв связи; при каждом reconnect клиент сверяется полным `GET /products`.
  В docker-compose SSE идёт через nginx (`proxy_buffering off` на `/api/`).
- **Покупка с бронью.** «Купить» → `POST /reservations` (атомарный захват единицы) → страница `checkout.html`
  с обратным отсчётом → «Оформить заказ» (`POST /orders {reservation_id}` по **текущей** цене) → эмуляция оплаты → выдача.
- **Поиск/фильтры.** Серверный `GET /products` (`q`, `type`, `seller`, `sort`, `in_stock`, `limit/offset`, `pg_trgm`),
  на клиенте debounce + AbortController + seq (устаревшие ответы отбрасываются) + состояние в URL (`?q=&type=&sort=&in_stock=`).

## Админка

`http://localhost:8080/admin.html` (локально открыта; при заданном `ADMIN_TOKEN` — Bearer-авторизация).
Что умеет: сверка «оплачен/не выдан», повторная выдача, **пополнение остатка**, **смена цены**
(публикует SSE — витрина обновляется мгновенно).

## Как воспроизвести (формат ответа по ТЗ)

### 1) Живое обновление витрины

1. Открыть http://localhost:8080 в двух вкладках.
2. Либо дождаться авто-изменения цен (`LIVE_SIMULATE=1`), либо в админке сменить цену/пополнить остаток
   любого SKU.
3. Цена/«Осталось N» меняются во второй вкладке **без перезагрузки** (< 1 c). Когда остаток уходит в 0,
   кнопка «Купить» становится недоступной у всех одновременно.
4. Обновите страницу или оборвите сеть — после reconnect витрина сверяется с сервером и показывает актуальное.

### 2) Покупка последней единицы наперегонки

Автоматическая проверка:

```bash
cd backend && npm test                      # 54 теста, в т.ч. reservation_race (N параллельных броней)
```

Ручная (два окна/профиля):

1. Найдите товар с бейджем «Осталось 1» (или в админке пополните на 1 единицу и раскупите до 1).
2. В двух окнах почти одновременно нажмите «Купить».
3. Одно окно уходит на checkout с обратным отсчётом; второе мгновенно получает «Только что раскупили»
   и предложение альтернативного продавца (или возврат к товару).
4. Если победитель не оплатил до конца отсчёта — бронь снимается, товар снова виден у всех.

## Ключевые решения этапа 2 (и апгрейд-пути)

1. **Гонка и бронь — атомарный conditional update в Postgres**, без очереди:
   `UPDATE stock_mirror SET held=held+1 WHERE sku=$1 AND available-held>=1`. Решение «кто взял» обязано
   быть синхронным и линеаризуемым на ресурсе; Kafka/Celery решают асинхронную доставку, а не эту гонку.
2. **`available − held` = «можно купить»**: физический пул ключей минус коммитнутые (брони +
   заказы created/paid/delivering). Инвариант «нет оплаченного заказа без товара»: выдано + held ≤ пул.
3. **Real-time — SSE + in-process шина**, публикация после COMMIT, heartbeat 25 c, снапшот на reconnect.
   Апгрейд-путь на несколько реплик API: `LISTEN/NOTIFY` Postgres → Redis pub/sub.
4. **Таймеры**: ленивое освобождение на read-пути (GET протухшей брони возвращает единицу) + sweeper
   в recovery-воркере как backstop; CAS `active→confirmed AND expires_at > now()` закрывает границу истечения.
5. **Выдача** осталась на transactional outbox этапа 1 (`delivery_jobs` + `SKIP LOCKED`). Прод-эволюция:
   CDC из outbox (Debezium) → Kafka для отдельного сервиса доставки — но на этом объёме внешний брокер
   избыточен и не улучшает критерии приёмки.
6. **Поиск** — `pg_trgm` GIN на `name` (тысячи офферов, EXPLAIN-тест). Elasticsearch/Meilisearch —
   при сотнях тысяч SKU и сложных фасетах.

Полный разбор решений и ограничений — [`docs/PLAN-stage2.md`](docs/PLAN-stage2.md) и `backend/README.md`.
