# Магазин цифровых товаров — тестовое задание

Ядро и витрина магазина цифровых товаров для геймеров (ключи, пополнения, подписки, гифт-карты).
Реализованы оба ТЗ: [бэкенд](tz-backend.md) (этапы 1–5) и [фуллстек](tz-fullstack.md) (этапы 1–4).

Смысловой центр задания — **однократная выдача под гонками, ловушка таймаута и восстановление
после сбоев**. Всё это покрыто тестами и воспроизводимыми скриптами, см. ниже.

- **Витрина (демо):** https://frontend-production-d819.up.railway.app
- **API:** https://api-production-7e83.up.railway.app · [`/health`](https://api-production-7e83.up.railway.app/health) · [`/products`](https://api-production-7e83.up.railway.app/products)
- **Затрачено времени:** 3,5 часа
- **Документация API:** [справочник](https://t-shell.uk/api-docs) · машиночитаемая спека [`backend/openapi.yaml`](backend/openapi.yaml) (OpenAPI 3.0.3, 11 операций)

## Запуск одной командой

```bash
cd backend
docker compose up -d --build
```

| Сервис | Адрес | Что это |
|---|---|---|
| `frontend` | http://localhost:8080 | Витрина (nginx, статика из `frontend/`) |
| `app` | http://localhost:3000 | REST API + фоновые воркеры выдачи и recovery |
| `supplier-a` / `supplier-b` | внутри сети compose | Заглушки поставщиков (падают и «зависают») |
| `db` | :5432 | PostgreSQL 16 |

Проверка: `curl http://localhost:3000/health` → `{"ok":true}`, витрина — http://localhost:8080.
Каталог засеивается автоматически при старте на чистой БД.

> Витрина берёт адрес API из `window.API_BASE`, по умолчанию `http://localhost:3000`.
> Для запуска целиком локально менять ничего не нужно.

Локальный запуск без Docker для приложения, переменные окружения и полный список
эндпоинтов — в [backend/README.md](backend/README.md).

### Развёрнутая версия

Проект целиком поднят на Railway (`tz-fullstack-shop`), пять сервисов:

| Сервис | Роль | Доступ |
|---|---|---|
| `frontend` | витрина (nginx) | публичный |
| `api` | REST + фоновые воркеры | публичный |
| `supplier-a`, `supplier-b` | заглушки поставщиков | только приватная сеть |
| `Postgres` | БД | только приватная сеть |

Поставщики наружу не смотрят — `api` ходит к ним по `*.railway.internal`.
Адрес API витрина берёт из `config.js`, который собирается на старте контейнера
из переменной `API_BASE`; локально файл указывает на `http://localhost:3000`,
так что запуск через `docker compose` работает без правок.

## Админка

`/admin/*` меняет остатки и запускает повторную выдачу, поэтому на публичном
деплое она закрыта токеном, а локально открыта.

| Где | Как войти |
|---|---|
| Локально (`docker compose up`) | `http://localhost:8080/admin.html` — токен не нужен, `ADMIN_TOKEN` не задан |
| Демо-деплой | `<витрина>/admin.html` — страница спросит токен при первом обращении |

Токен для демо передаётся отдельно от репозитория (в форме/письме), в гит не коммитится.
Страница спрашивает его только после `401`, запоминает в `localStorage` и сбрасывает,
если сервер токен не принял.

Через curl:

```bash
curl -H "Authorization: Bearer $ADMIN_TOKEN" <api>/admin/reconciliation
```

## Ответы по ТЗ

### Как воспроизвести проверку гонок и отказ/фолбэк поставщика

Нужен только Postgres — `docker compose up -d db`. Оба скрипта самодостаточны:
поднимают одноразовую БД (`shop_race_<pid>` / `shop_demo_<pid>`), свой экземпляр
приложения и свои заглушки поставщиков, а после прогона удаляют БД за собой.
Дев-база `shop` не затрагивается, и запущенный `app` не мешает.

```bash
cd backend
npm run race-check              # 50 параллельных вебхуков «paid» по одному заказу
npm run supplier-failure-demo   # поставщик A всегда 5xx -> fallback на B
npm test                        # 37 тестов, все критерии приёмки обоих ТЗ
```

`race-check` создаёт заказ, шлёт 50 одновременных вебхуков с разными `event_id`,
доводит выдачу и печатает отчёт. Ожидаемое: `order_status: delivered`,
`successful_delivery_attempts: 1`, `ledger_payment_entries: 1`, все ответы `200`.

`supplier-failure-demo` поднимает A с `errorRate=1`. В отчёте видно две неудачные
попытки к A и одну успешную к B, заказ `delivered`, ключ выдан один раз.

Изоляция по БД здесь не косметика. Без неё воркер запущенного `app` перехватывает
задачу через `FOR UPDATE SKIP LOCKED` и идёт в свои заглушки поставщиков, чей пул
ключей скрипту не принадлежит — и проверка падает на полностью исправной системе.

Отдельные сценарии, если нужно точечно:

```bash
npm run test:race                                   # только гонка вебхуков
node --test test/timeout.test.js                    # таймаут поставщика, выдавшего код
node --test test/fallback.test.js                   # A недоступен -> B
node --test test/out_of_order.test.js               # вебхук раньше заказа
node --test test/stock.test.js                      # пустой остаток -> восстановление
node --test test/promocode.test.js                  # лимит промокода под нагрузкой
```

### Ключевые решения и масштабирование

**Внешних брокеров нет — все гарантии на Postgres.** Очередь выдачи это таблица
`delivery_jobs` (transactional outbox): задача ставится в той же транзакции, что и
перевод заказа в `paid`, поэтому «оплатили, но задачу потеряли» невозможно
в принципе. Для тестового это надёжнее и проверяемее, чем RabbitMQ или Kafka сбоку.

**Однократность собрана из четырёх независимых замков**, каждый из которых
выдерживает параллельность сам по себе:

1. `payment_events.event_id` — PRIMARY KEY. Повтор вебхука не вставляется и ничего
   не меняет. Событие по ещё не созданному заказу ложится с `order_fk = NULL`
   и применяется при создании заказа — вебхук вне порядка не теряется.
2. Переход оплаты — CAS: `UPDATE ... WHERE order_id=$1 AND status='created'`.
   Из 50 параллельных вебхуков выигрывает ровно один, остальные становятся no-op.
3. Частичный уникальный индекс `uq_delivery_jobs_active` на `order_id WHERE status
   IN ('pending','processing')` — активная задача на заказ всегда одна. Воркеры
   разбирают их через `FOR UPDATE SKIP LOCKED`, поэтому горизонтальное
   масштабирование воркеров не требует ни лидера, ни распределённого лока.
4. `delivery_attempts.request_id` — PRIMARY KEY, и поставщик обязан на повтор с тем
   же `request_id` вернуть тот же код. Отсюда главное: **таймаут не равен отказу**.
   Поставщик мог выдать код и не донести ответ; повтор после таймаута забирает
   тот же самый код, а не выпускает второй.

**Деньги.** `money_ledger` с `UNIQUE(order_id, entry_type)` — ровно один платёж на
заказ. Сумма журнала всегда равна сумме оплаченных заказов, это проверяется
эндпоинтом сверки и тестом, а не декларируется.

**Сбои не роняют заказ.** `out_of_stock` и `delivery_failed` — восстановимые
состояния: заказ остаётся в очереди, фоновый воркер доводит его после пополнения
остатка, либо оператор дожимает через `POST /admin/orders/{id}/redeliver`.
Повторный вызов на уже выданном заказе возвращает `changed: false`.

**Повторы к поставщикам** — экспоненциальный бэкофф `backoffBaseMs * 2^n`,
сначала A, при исчерпании попыток fallback на B. Доли ошибок и таймаутов у обеих
заглушек задаются переменными окружения, поэтому любой сценарий воспроизводим.

**Под нагрузкой** я бы двигался в таком порядке:

- *Витрина каталога.* Остаток уже вынесен в `stock_mirror` и обновляется
  транзакционно — горячий запрос не считает агрегат по журналу выдач, а читает
  готовую строку по первичному ключу. Есть индекс по `products(type)` под фильтр.
  Проверено на 5000 SKU: план идёт по индексам (`test/catalog.test.js`).
  Дальше — покрывающий индекс под конкретный запрос витрины и кэш в Redis
  с инвалидацией по событию выдачи.
- *Воркеры выдачи.* Масштабируются репликами без изменений кода: `SKIP LOCKED`
  уже разводит их по разным задачам. Упрутся — партиционировать `delivery_jobs`
  по статусу и убирать `done` в архив, чтобы горячая часть таблицы оставалась
  маленькой.
- *Вебхуки.* Обработчик отвечает быстро и делает минимум работы, тяжёлое уносится
  в очередь. При росте — принимать событие, писать в `payment_events` и отвечать
  `200`, а применение статуса делать отдельным воркером; схема это уже допускает,
  `applied_at` для того и заведён.
- *БД.* Первый предел — блокировки на `orders` при обновлении статуса. Лечится
  шардированием по `order_id` и выносом read-only нагрузки (витрина, сверка) на
  реплику. `money_ledger` со временем партиционировать по месяцам.

## Структура

```
backend/     ядро: API, вебхук, выдача, поставщики-заглушки, воркеры, тесты, README
frontend/    витрина: index.html + order.html (статус заказа) + admin.html (админка)
tz-backend.md, tz-fullstack.md   исходные ТЗ
```

### Витрина

Верхняя часть свёрстана по макету: шапка, баннер-карусель, ряд иконок сервисов, блок
пополнения, карточки товаров. Пять обязательных интерактивов на месте — карусель
(автопрокрутка, стрелки, точки), меню «Каталог» (открытие/закрытие по клику и вне меню),
переключатель валют, hover-выделение иконок и карточек. Покупка идёт с кнопки «Купить»:
создание заказа → оплата (кнопки «успех/неуспех» шлют вебхук по контракту) → автовыдача
ключа → страница статуса. Промокод применяется на сервере, клиентской сумме доверия нет.

Сверх ТЗ добавлены блок отзывов, футер и пересчёт валют — задание их не требовало.
